# Update 7.0.0

## 버전

- 출발 버전: `6.1.0`
- 대상 버전: `7.0.0`

## 주요 변경

- Service와 application use case의 비즈니스 동작을 단위 테스트 기반 TDD로 구현합니다.
- Controller는 비즈니스 규칙을 소유하지 않고 Web/API 경계 테스트와 Spring REST Docs 문서를 담당합니다.
- Repository와 전체 application 통합 테스트는 실제 기술 의미가 필요한 범위로 제한합니다.
- Spring Boot에서 관계형 Database를 사용하면 Flyway를 필수 schema migration 도구로 사용합니다.
- Requirement와 Microsoft Excel 테스트 문서에 테스트 유형과 책임 계층을 기록합니다.

## 호환성

Service 구현 순서와 Spring Boot 관계형 Database의 schema 관리 도구를 의무화하므로 이전 개발 절차와 호환되지 않는 MAJOR update입니다.

[Service 단위 테스트 TDD]

standards/backend/BE-04-testing-convention.md의 STD-BE-040과 STD-BE-041을 유지하고 STD-BE-042부터 STD-BE-049까지 다음 규칙을 추가하세요.

1. Service와 application use case의 새 비즈니스 동작은 production code보다 실패하는 단위 테스트를 먼저 작성합니다.
2. Service 단위 테스트는 framework context를 시작하지 않고 repository, 외부 API와 메시지 같은 경계를 mock 또는 fake로 대체합니다.
3. 정상 결과와 주요 실패 조건은 각각 독립된 테스트로 작성하고 하나의 테스트는 하나의 비즈니스 결과만 검증합니다.
4. 테스트가 의도한 미구현 동작 때문에 실패하는지 확인한 뒤 최소 코드를 작성하고, 통과 상태에서 책임 분리와 중복 제거를 수행합니다.
5. 하나의 실패 조건은 이를 판단하는 Service 또는 domain 책임의 테스트가 소유하며 다른 계층에서 같은 비즈니스 판단을 중복하지 않습니다.
6. private method를 직접 테스트하지 않으며 독립적인 비즈니스 책임이면 domain object나 policy로 추출해 공개 동작으로 검증합니다.
7. Controller는 비즈니스 규칙을 소유하지 않고 HTTP mapping, 입력 validation, 인증 주체 전달, Service 결과와 오류의 응답 변환만 검증합니다.
8. Repository의 기본 CRUD를 반복 검증하지 않고 custom query, mapping, constraint와 transaction처럼 실제 persistence 의미가 중요한 동작만 통합 테스트합니다.

standards/backend/README.md에서 Backend 테스트 문서의 내용을 Service 단위 TDD와 필요한 통합 테스트로 설명하세요.

[Controller와 API 문서]

standards/backend/spring-boot/BE-SPR-05-testing-convention.md에 STD-BE-SPR-057부터 STD-BE-SPR-059까지 다음 규칙을 추가하세요.

1. Controller는 @WebMvcTest 등 Web/API 경계 테스트로 검증하고 Service를 대체해 비즈니스 규칙을 중복 검증하지 않습니다.
2. API 문서는 통과하는 Controller 테스트에서 Spring REST Docs로 생성하며 request, response, 인증과 계약의 주요 오류를 포함합니다.
3. @SpringBootTest 전체 통합 테스트는 핵심 사용자 흐름, bean wiring 또는 실제 경계 연결에만 사용하고 모든 Controller에 반복하지 않습니다.

[Flyway]

standards/backend/spring-boot/BE-SPR-06-flyway-convention.md를 만들고 STD-BE-SPR-060부터 STD-BE-SPR-069까지 다음 규칙을 정의하세요.

1. Spring Boot에서 관계형 Database를 사용하면 Flyway를 schema migration 도구로 사용합니다.
2. 실행 가능한 schema는 Flyway migration이 소유하고 Hibernate ddl-auto는 validate 또는 none만 사용하며 create, create-drop과 update로 schema를 생성하거나 변경하지 않습니다.
3. versioned migration은 src/main/resources/db/migration 아래에 V<version>__<description>.sql 형식으로 둡니다.
4. 적용된 versioned migration을 수정하거나 삭제하지 않고 수정은 새 migration으로 작성합니다.
5. repeatable migration은 view와 function처럼 전체 정의를 안전하게 재적용할 수 있는 객체에만 사용합니다.
6. schema와 필수 기준 데이터만 포함하고 sample, 개발 및 테스트 데이터는 분리합니다.
7. application과 migration 계정 권한을 가능한 범위에서 분리하고 비밀정보를 migration에 넣지 않습니다.
8. transaction block에서 실행할 수 없는 DDL은 별도 migration으로 분리하고 실행 방식을 명시적으로 구성합니다.
9. production 호환 실제 Database에서 빈 schema와 지원하는 이전 schema의 순차 적용을 검증합니다.
10. application 시작 검증에서 Flyway 성공과 허용되지 않은 pending 또는 failed migration 부재를 확인하고, JPA를 사용하면 mapping과 schema 일치도 검증합니다.

standards/backend/spring-boot/README.md에 새 Flyway 문서를 등록하고 standards/database/README.md에서 Spring Boot 관계형 Database가 이 규칙을 적용하도록 연결하세요.
